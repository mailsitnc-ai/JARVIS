2026-09-20: ported JARVIS to run natively on **macOS as well as Windows** — one codebase, not a fork. Pushed to GitHub **https://github.com/mailsitnc-ai/JARVIS** (branch `master`) so the user can `git clone` it onto their MacBook's Desktop. Repo owner account: `mailsitnc-ai`. Git Credential Manager handles auth (browser sign-in on push).

Design: new **`core/oslayer.py`** is the platform layer — every OS-specific op branches on `sys.platform` there (`IS_WINDOWS`/`IS_MAC`/`IS_LINUX`), and the rest of the code calls it instead of Windows APIs. Ported: user data dir (%APPDATA% vs ~/Library/Application Support), open files/folders/apps (`os.startfile` vs `open`/`open -a` + a Windows→mac app alias table), TTS (PowerShell SAPI vs macOS `say`), screenshots (GDI vs `screencapture -x`), notifications (MessageBox vs `osascript`), gesture scroll (ctypes mouse_event vs Quartz), running user programs (pythonw/.bat vs python3 + Terminal.app/.command), Chrome path + debug profile, memory/battery/CPU (winsys/system_status), keystore (DPAPI on Win; base64 chmod-600 file elsewhere — prefer env vars), daemon spawn (detached), start-at-login (Startup .lnk vs LaunchAgent). `window_manager/win32.py` + `hotkey.py` import safely off-Windows with fallbacks (panel = plain window, no side-docking; global hotkey via `pynput` on mac).

IMPORTANT gotcha: `core/actions.py` must stay importable by the sandbox harness (loaded by PATH under `python -I`, nothing else from JARVIS importable). So it loads oslayer via the `_osl()` helper (tries `from . import oslayer`, falls back to loading `oslayer.py` by path). Don't add plain `from .oslayer import ...` to actions.py — it breaks the sandbox. oslayer itself is stdlib-only on purpose.

LIVE-VERIFIED ON THE MAC 2026-09-20 (Shivam's MacBook Neo, `~/Desktop/JARVIS`, system Python 3.9.6): `jarvis doctor` shows the macOS data dir (~/Library/Application Support/JARVIS) and macOS RAM detection (sysctl/vm_stat) working; 32 skills load; `ask "what time..."` routes to current_time; `setkey groq/gemini` + a cloud groq call work; `write_file` wrote primes.py AND a **primes.command** launcher (the cross-platform launcher), smoke-run "verified it runs" on python3. So core, keys, cloud LLM, skills, file write + `.command` launcher, and pyverify all work natively on macOS. The pip install of `requirements-extras.txt` (pyobjc/pynput) fails on the bare Command Line Tools Python 3.9 + broken MacOSX SDK - those are optional (gesture-scroll + hotkey); base `requirements.txt` is wheel-only (opencv, websocket-client). Google OAuth VERIFIED on the Mac too (2026-09-20): `jarvis google setup` + `jarvis google login` connect (browser flow) and `search my google docs` returns real results (found "INS Document of HOPE"). Fixed a bug where core/google.py called keystore._dpapi directly (crashed on mac) - now uses keystore._encode/_decode.
