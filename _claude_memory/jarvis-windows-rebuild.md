On 2026-09-13 JARVIS 1.0 was rebuilt from scratch in this folder as a Windows-native port of an earlier macOS build; the user pasted the lost chats as the spec.

LLM providers (updated 2026-09-14): the user reversed the earlier local-only stance and asked for a powerful API with generous limits. Chain: `llm.fallback_order = [groq, gemini, ollama]` (MiniMax dropped — needs a company account; Mistral removed at user request for now, but the generic `OpenAICompatProvider` makes re-adding any OpenAI-compatible provider trivial: subclass with name/base_url/token_param + add to PROVIDERS + config + ENV_VARS). Groq/Gemini are OpenAI-compatible via `OpenAICompatProvider` in `core/llm_router.py` (Groq uses max_completion_tokens, Gemini max_tokens). Keys via `jarvis setkey groq|gemini` (DPAPI, `core/keystore.py` ENV_VARS). Cloud only activates when a key exists; else falls through to local Ollama `qwen2.5-coder:0.5b-instruct-q8_0`. Router retries 429/5xx then falls through. `setkey` must never pin `llm.provider` (old bug). All three free tiers may train on prompts — keep private data on local Ollama. Honest framing given to user: a strong API fixes the *builder* (skills stop being dumb) which is ~80% of "feels self-evolving", but nothing retrains the model; true-ish self-evolving = strong builder + a learning loop (not yet built) + accumulated skills.

Web apps + skill composition (added 2026-09-14): `core/actions.py` has WEB_APPS map + `web_url_for()` + `strip_browser_suffix()` so "open google docs / gmail / youtube / <domain>" opens the site and "on my chrome" is ignored; `open_app` and `browser_tab` skills use them. Skill composition: `context["run"]("sub request")` routes a sub-request through existing skills only (no evolution), depth-capped at 3, via `Jarvis._subrun`/`_execute(depth=)`; documented in the drafter prompt and stubbed in the sandbox harness. Known limitation the user still feels ("a bit dumb"): routing is deterministic keyword/regex + web-app map, not deep comprehension; unknown sites need a domain or fall to search, and messy multi-step queries chain crudely. LLM-first understanding (rewritten 2026-09-14 after "still doesn't understand multistep/intent even with 3 AIs"): `core/planner.py` was REPLACED by `core/understand.py`. When a cloud brain is available (`Jarvis._use_planner()`: first available provider != ollama; FakeLLM returns False so tests use rules), `_fast` -> `_fast_cloud` sends anything non-trivial through one `understand()` call returning intent chat|act|preference. act -> ordered steps run via `_run_step` (existing skill else build; `_clean_step` strips a leading skill-name the model sometimes prepends), route "planned" (multi) / "understood" (single). chat -> reply. preference -> `_apply_preference` writes an ALLOWED_SETTINGS key via set_user_value, coerces the value, and for llm.* rebuilds `self.llm`/`self.evolution.llm` live (so "use gemini as my main model" / "switch back to groq" work instantly and persist). Local-only path `_fast_local` keeps the old rules (`_chain`, triggers, `_interpret`). Instant obvious single-trigger commands still bypass the LLM. Earlier fix kept: `strip_browser_suffix` no longer greedy.

Learning loop (added 2026-09-14): `memory/learning.py` LearningStore persists `memory/data/route_hints.json` (keyword-set -> skill) and `lessons.jsonl`. Learned routes come from reuses (auto) and `jarvis teach <skill> <phrase>` / panel `/teach` (explicit); `Jarvis.candidates()` appends hinted skills after trigger matches so a taught/learned phrasing routes without rebuilding. Lessons come from build failures + skill crashes and are injected into the drafter prompt (`draft_skill(..., lessons=)`) so the model stops repeating mistakes. View: `jarvis lessons` / `/lessons`; clear: `jarvis lessons --clear`; doctor shows counts. Deterministic and conservative on purpose (no free self-rewriting). This is the "genuinely self-evolving" piece that works regardless of model — it improves routing/building from usage.

Capable agent (added 2026-09-14, answering "why hardcode, it should figure out how and do it regardless"): added `network` permission + `ActionBroker.http_request(url,...)` (gated; dry-run returns "{}" so JSON parsers survive verification). Evolved skills now fetch live data via `context["actions"].http_request` (drafter prompt updated); raw urllib/socket/http/requests are blocked in skills so all network is gated. `handle_missing(request, build_only=True)` (via `_run_step`/`_evolve_new(build_only=True)`) forces a BUILD instead of answering with a snippet when the understanding layer already decided it's a task — this is what makes "what's the price of bitcoin" write a CoinGecko skill and return the real number (verified live, ~4s). Multi-step ("act", >=2 steps) requests get a plan-review: the plan is shown and `self.confirm` must approve (deny -> route "cancelled") before running. Guardrails kept on purpose (sandbox, permissions, ALLOWED_SETTINGS) - the honest line given to the user: "do anything regardless" vs "safe on your real machine" conflict is resolved by "do far more, behind a gate you control," not by removing limits. Adaptive retry loop (added 2026-09-14): `Jarvis._execute` now treats an evolved skill as failed not only when it raises but when it RETURNS a swallowed error (regex `_FAILURE_OUTPUT`: traceback/no module named/could not be imported/XError/is not defined/"failed to \\w"/etc., conservative so legit "not found"/"no results" answers don't trigger). On failure it calls `evolution.repair` (redraft+verify+install with the failure as feedback) and re-runs, `repairs_left=2`. Drafter contract updated: don't swallow real bugs, let them raise. Combined with the package auto-install-on-missing-module (in `_verify`), a live QR build installed qrcode then auto-installed pillow and produced a real QR (~9s). Builtins aren't repaired (returned as-is). Known caveat: repair re-runs run() so non-idempotent side effects could repeat (bounded to 2).

Package installation (added 2026-09-14): `packages` permission + `ActionBroker.install_package(name)` (validates name via `_VALID_PACKAGE`, pip install --user unless in venv, then `_make_installed_packages_importable()` adds user-site to sys.path so the running daemon can import it without restart). Skills declare `SKILL["requires"]=[...]`; `enforce_skill_meta` preserves it; `EvolutionEngine._verify` installs declared requires then, on a sandbox "No module named X", installs MODULE_TO_PIP.get(X,X) and re-verifies (up to 3x). Orchestrator passes `installer=self._install_package` (gated broker) to the engine. Sandbox now runs WITHOUT `-I` and keeps APPDATA/LOCALAPPDATA in the scrubbed env so user-site packages import during verification; API keys still stripped. Network libs (urllib/socket/http/requests/httpx/ftplib) stay blocked in skills -> network via `http_request` only. Verified live: "make an ascii qr code" -> built skill, pip-installed qrcode, printed a real QR (~8s). Known rough edge: a skill that catches its own errors and returns a message (instead of raising) masks bugs and skips self-repair; and model library-usage is hit-or-miss (first qr draft used a nonexistent qrcode helper, a fresh rebuild got it right).

Behaviours carried over from the old chats, keep them:
- Routing: no trigger match is handled by the dispatcher (chat/skill/build), not blind evolution.
- Greetings/knowledge questions answered directly; action-verb requests become skills.
